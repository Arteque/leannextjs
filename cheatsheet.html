12 · 2026-10-03 · Imports

Path Aliases

Concept. A path alias is a nickname for a folder, so you can import from anywhere without counting ../ hops. Next.js reads the paths and baseUrl options straight out of tsconfig.json — no extra setup.

// tsconfig.json  -- "@/" now means "the project root"
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./*"]
    }
  }
}
// Before: breaks the moment you move the file
import Button from "../../../components/Button";

// After: same path from anywhere
import Button from "@/components/Button";

The alias does not check spelling

Everything after @/ goes straight to the filesystem — capital letters included. Windows and macOS are case-insensitive: ask for Components/Button.tsx and you get components/Button.tsx. Linux is case-sensitive: there the same import is a file that does not exist.

Think of a receptionist. Windows is the friendly one — “close enough” — and hands you the key. Linux is the strict one: wrong spelling, no key. Your laptop is friendly. The deploy server is strict.

So a casing typo is invisible locally and fatal on deploy: Module not found: Can't resolve '@/Components/Button'. TypeScript catches it first if you ask it to:

npx tsc --noEmit

# error TS1261: Already included file name '.../Components/Button.tsx'
#   differs from file name '.../components/Button.tsx' only in casing.
Common mistakes
  • Mixing cases in one project (@/components in one file, @/Components in another). The bundler then builds two copies of the same component, and Fast Refresh silently stops working for it.
  • Renaming the folder to match the imports. Git is usually set to core.ignorecase true, so a casing-only rename is never recorded — the repo keeps the old name and the deploy still fails. Use git mv -f, or just fix the imports.
  • Trusting the dev server. It happily serves a casing bug. Only tsc and Linux complain.
Next: add a "typecheck": "tsc --noEmit" script to package.json. Since TypeScript 5.0, forceConsistentCasingInFileNames is on by default, so it catches casing bugs with no config.

11 · 2026-10-03 · Icons

Icon Libraries

Concept. An icon library gives you icons as inline SVG — a picture written as code, rendered right inside your HTML. You import only the icons you use, so only those ship. The old alternative, an icon font loaded from a CDN, makes every visitor download all ~1,400 glyphs to show five.

Font Awesome’s React packages are the common choice. Install the engine, the component, and the icon sets you want:

npm install @fortawesome/fontawesome-svg-core @fortawesome/react-fontawesome \
  @fortawesome/free-solid-svg-icons @fortawesome/free-brands-svg-icons

Three lines in the root layout

// app/layout.tsx
import { config } from "@fortawesome/fontawesome-svg-core";
import "@fortawesome/fontawesome-svg-core/styles.css";
import "./globals.css";

config.autoAddCss = false;

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}

Importing the stylesheet puts it in the server-rendered HTML, so icons are the right size on the very first frame. autoAddCss = false then tells Font Awesome not to inject that CSS a second time at runtime.

Using one

// components/IconLink.tsx
import { FontAwesomeIcon } from "@fortawesome/react-fontawesome";
import { faGithub } from "@fortawesome/free-brands-svg-icons";

export default function IconLink() {
  return (
    <a href="https://github.com" aria-label="GitHub">
      <FontAwesomeIcon icon={faGithub} className="text-2xl" />
    </a>
  );
}

An icon is 1em tall and takes the current text colour, so size and colour it like a word: className="text-2xl text-orange-600". It renders to plain SVG on the server, so it needs no "use client" and ships no JavaScript.

Naming an icon-only link

An icon is decoration, so Font Awesome renders it with aria-hidden="true" unless you label it. That is the right default — but it means a link containing only an icon has no text whatsoever, and a screen reader announces it as just “link”. You have to supply the name yourself, and there are two ways:

// Option A -- aria-label on the link
<Link href="https://github.com" aria-label="GitHub">
  <FontAwesomeIcon icon={faGithub} />
</Link>

// Option B -- real text, hidden visually
<Link href="https://github.com">
  <span className="sr-only">GitHub</span>
  <FontAwesomeIcon icon={faGithub} />
</Link>

Both give the link the same accessible name. Option B is the sturdier one: it is real text in the page, so browser and in-page translation tools translate it, whereas an aria-label is routinely skipped by them. sr-only is a built-in Tailwind utility that clips the text to a 1px box — invisible on screen, still read aloud.

Either way, label the link, not the icon. Font Awesome 7 deprecated the icon’s own title and titleId props for exactly this reason.

Common mistakes
  • A giant icon flashes on load. The stylesheet import or autoAddCss = false is missing.
  • An icon-only link with no label. The icon is hidden from assistive tech on purpose, so the link carries no text at all and is announced as just “link”. Give it a name — see above.
  • Importing a whole set with library.add(fas). That ships every icon. Import them one by one by name.
  • Sizing with h-6 or size-6. Font Awesome’s own stylesheet sets the height and wins. Use font-size utilities instead.
Next: the react-icons package bundles the same free icons with no CSS setup — handy when you only need a handful.

10 · 2026-10-03 · Structure

Component Folders

Concept. Next.js is unopinionated about where your code lives. Only app/ is special, and inside it only the reserved filenames mean anything. Everything else — components/, lib/, hooks/ — is purely your own convention.

Flat: fine until about 20 components

app/
  layout.tsx
  page.tsx
components/
  Button.tsx
  Card.tsx
  Header.tsx
lib/
  formatDate.ts

Layered: group by how composed a component is

This is atomic design: small pieces combine into bigger ones, and the folder tells you which level you are at. The rule is one-way — a layer may import from layers below it, never above.

components/
  atoms/        # smallest pieces: Button, Input, Logo
  molecules/    # a few atoms together: SearchBox, NavItem
  organisms/    # whole sections: Header, Footer, Sidebar

Colocation: keep a component next to the route that owns it

A folder inside app/ only becomes a URL when it contains a page.tsx. So you can safely keep route-specific files beside the route. Prefix a folder with _ to make it private and guarantee the router ignores it entirely.

app/
  blog/
    page.tsx          -> /blog
    _components/
      PostCard.tsx    -> not a route, never will be
Common mistakes
  • Reaching for atoms and molecules on day one. Three folders holding one file each is harder to navigate than one flat folder. Start flat, split when it actually hurts.
  • Thinking every file in app/ becomes a URL. Only page.tsx creates a route. A stray page.tsx in a helper folder, though, will quietly publish a URL.
  • Importing upward — an atom pulling in an organism. That makes the layers meaningless and invites circular imports.
Next: read up on route groups, (name), which group routes for a shared layout without adding a URL segment.

09 · 2026-09-25 · Components

Wrapper Components

Concept. A wrapper is a component whose job is to render another component with some decisions already made. It is the right tool when you keep repeating the same props — and dead weight when it only forwards them.

The test: can you name what this layer decides? If not, delete it and use the inner component directly.

Earns its place: it decides something

// components/ButtonLink.tsx
import Link from "next/link";
import type { ComponentProps } from "react";

export default function ButtonLink({
  className = "",
  ...props
}: ComponentProps<typeof Link>) {
  return (
    <Link
      className={`rounded bg-blue-600 px-4 py-2 text-white ${className}`}
      {...props}
    />
  );
}

It owns the button look. Every call site gets it for free, and one edit restyles them all.

Dead weight: it decides nothing

// Adds no styles, no defaults, no behaviour -- just a longer stack trace
export default function MyLink(props: ComponentProps<typeof Link>) {
  return <Link {...props} />;
}
Common mistakes
  • Chains three deep where the middle layer only forwards props. Each hop is one more file to open when you debug. Collapse it.
  • Wrapping “in case we need it later.” Adding the layer when you need it costs one small edit; carrying it meanwhile costs every reader.
  • Overwriting className instead of merging it. Then callers can never adjust spacing, and they reach past your wrapper.
Next: look at the clsx and tailwind-merge packages — they merge conflicting utility classes properly.

08 · 2026-09-21 · Routing

Routing Conventions

Concept. Next.js uses file-system routing: folders inside app/ become URL segments, and a handful of reserved filenames give a folder its behaviour. You never register a route anywhere — you create a folder.

app/
  layout.tsx          # shell wrapped around everything
  page.tsx            # /
  about/
    page.tsx          # /about
  blog/
    page.tsx          # /blog
    [slug]/
      page.tsx        # /blog/hello-world
  (marketing)/
    pricing/
      page.tsx        # /pricing   <- "(marketing)" is not in the URL

The reserved filenames

  • page.tsx — the UI for this URL. Without it, the folder is not a route.
  • layout.tsx — shared shell for this folder and everything under it. Keeps state on navigation.
  • loading.tsx — shown while the page loads.
  • error.tsx — shown if the page throws.
  • not-found.tsx — shown for a missing page.
  • route.ts — an API endpoint instead of a page.

The folder name conventions

  • [slug] — dynamic: matches any value and hands it to you as a param.
  • (name) — route group: groups routes for a shared layout, adds nothing to the URL.
  • _name — private: the router ignores it, so it is a safe home for helpers.
Common mistakes
  • Creating app/about.tsx and expecting /about. A route needs a folder with a page.tsx inside: app/about/page.tsx.
  • Looking for a pages/ folder. That is the old Pages Router. Modern Next.js uses app/, and the two use different APIs — most pre-2023 tutorials teach the old one.
  • Forgetting the default export in page.tsx. A named export is not picked up.
Next: try a dynamic route and read its param, then look at generateStaticParams for pre-rendering the known ones.

07 · 2026-09-21 · Navigation

Active Nav Links

Concept. Next.js does not build a nav out of your route folders. Routes are discovered at build time, but there is no list of them you can read at runtime — and that is deliberate: you rarely want every route in the menu, in folder order, with folder names as labels.

So you declare the menu yourself, in one array, and highlight the current item with usePathname.

// lib/routes.ts  -- one place to edit the menu
export const routes = [
  { href: "/", label: "Home" },
  { href: "/about", label: "About" },
  { href: "/blog", label: "Blog" },
];
// components/SiteNav.tsx
"use client";

import Link from "next/link";
import { usePathname } from "next/navigation";
import { routes } from "@/lib/routes";

export default function SiteNav() {
  const pathname = usePathname();

  return (
    <nav>
      <ul className="flex gap-4">
        {routes.map(({ href, label }) => {
          const active =
            href === "/" ? pathname === "/" : pathname.startsWith(href);

          return (
            <li key={href}>
              <Link
                href={href}
                aria-current={active ? "page" : undefined}
                className={active ? "font-bold underline" : ""}
              >
                {label}
              </Link>
            </li>
          );
        })}
      </ul>
    </nav>
  );
}

usePathname is a hook, so this file needs "use client" at the very top. That is not a downside — it still renders to HTML on the server for the first paint, and the component is downloaded once rather than re-fetched on every navigation.

Common mistakes
  • Forgetting "use client". You get an error about hooks only working in Client Components. Reading the URL in a Server Component is not supported at all.
  • Comparing with === only. Then /blog/my-post does not light up the Blog tab. Use startsWith — but special-case /, or Home stays active everywhere.
  • Reaching for window.location. It does not exist during server rendering, and it does not re-render on navigation.
  • Styling the active link with colour alone. Add aria-current so screen readers announce it too.
Next: look at useLinkStatus for showing a pending indicator while a navigation is in flight.

06 · 2026-09-21 · Routing

Pages and Layouts

Concept. A page.tsx is an ordinary React component that happens to live at a URL. There is no special syntax, no registration, no base class — the only rules are the filename and a default export.

// app/about/page.tsx  ->  /about
export default function AboutPage() {
  return <h1>About us</h1>;
}

That is a complete page. The filename does the routing; the function is just React.

A layout is the shell around pages

A layout.tsx wraps every page beneath it and receives them as children. On navigation it is not re-rendered — it keeps its state, so a sidebar scroll position or an open menu survives.

// app/blog/layout.tsx  -- wraps /blog and everything under it
export default function BlogLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <section>
      <h2>Blog</h2>
      {children}
    </section>
  );
}

The root layout, app/layout.tsx, is the one exception with a real requirement: it must render the <html> and <body> tags, because nothing else does.

// app/layout.tsx
import "./globals.css";

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}
Common mistakes
  • A named export instead of export default. Next.js looks only for the default export, so the route 404s or errors.
  • A layout that forgets to render children. The page vanishes and the layout looks fine — a confusing blank screen.
  • Expecting a layout to re-run on navigation. It does not. Anything that must react to the URL belongs in the page, or in a Client Component reading usePathname.
Next: add a loading.tsx next to a page and watch Next.js show it automatically while the page loads.

05 · 2026-09-21 · Styling

Tailwind v4 Utilities

Concept. Tailwind v4 is configured in CSS, not in a JavaScript config file. One @import replaces the old three @tailwind directives, @theme defines your design tokens, and @utility defines your own utility classes.

/* app/globals.css */
@import "tailwindcss";

@theme {
  --color-brand: #517ea3;
  --font-title: var(--font-oswald);
}

@utility card {
  border-radius: 0.75rem;
  background: white;
  padding: 1.5rem;
}

A token in @theme becomes utilities automatically: --color-brand gives you bg-brand, text-brand, border-brand. And a custom utility gets every variant for free — hover:card and md:card work with no extra config.

The name takes no dot

@utility wants the utility name, not a CSS selector. This is the single most common v4 slip:

/* Wrong -- that is a CSS selector, and v3 muscle memory */
@utility .card { ... }

/* Right -- just the name */
@utility card { ... }

In v3 you wrote whole selectors inside @layer utilities, so the dot belonged there. In v4 the dot is implied, exactly like Tailwind’s own flex or p-4. Leave it in and the class silently never generates.

Common mistakes
  • Looking for tailwind.config.js. v4 does not need one. Most tutorials still tell you to edit it.
  • Using the v3 directives @tailwind base / components / utilities. In v4 it is the single @import "tailwindcss".
  • Naming a utility after one Tailwind already owns, like container. You override the built-in and confuse every reader. Pick a distinct name.
  • Building class names at runtime, e.g. `text-${color}-500`. Tailwind scans your source as plain text, so that class is never generated. Write the full class names out.
Next: read about @theme inline — it keeps your tokens referring to CSS variables, which is what makes dark mode easy.

04 · 2026-09-21 · updated 2026-10-03 · TypeScript

Typing Props

Concept. ComponentProps borrows the prop types of something that already exists, instead of you retyping them. It is the one React type worth learning early, because it keeps a wrapper in sync with whatever it wraps — for free, forever.

Wrapping an HTML element

// components/Container.tsx
import type { ComponentProps } from "react";

export default function Container({
  className = "",
  ...props
}: ComponentProps<"div">) {
  return <div className={`mx-auto max-w-5xl ${className}`} {...props} />;
}

ComponentProps<"div"> means “every prop a real div accepts” — id, onClick, children, aria-*, all of it. Swap in "button" or "a" for those elements.

Wrapping another component

// components/NavLink.tsx
import Link from "next/link";
import type { ComponentProps } from "react";

export default function NavLink(props: ComponentProps<typeof Link>) {
  return <Link className="underline" {...props} />;
}

When your wrapper supplies a prop, remove it

Borrowed types come with borrowed requirements. If you wrap an image and hard-code the src yourself, callers are still forced to pass one — until you Omit it:

// components/Logo.tsx
import Image from "next/image";
import type { ComponentProps } from "react";

type LogoProps = Omit<ComponentProps<typeof Image>, "src" | "alt">;

export default function Logo(props: LogoProps) {
  return <Image src="/logo.svg" alt="Logo" {...props} />;
}

Now <Logo width={120} height={40} /> type-checks, and nobody can pass a conflicting src.

When your wrapper adds a prop, intersect it

Omit takes props away. To add props of your own, join the borrowed type to your own with & — TypeScript’s “and also” for object types.

// components/IconLink.tsx
import Link from "next/link";
import type { ComponentProps } from "react";
import { FontAwesomeIcon } from "@fortawesome/react-fontawesome";
import type { IconProp } from "@fortawesome/fontawesome-svg-core";

type IconLinkProps = Omit<ComponentProps<typeof Link>, "children"> & {
  icon: IconProp;
  label: string;
};

export default function IconLink({
  icon,
  label,
  className = "",
  ...props
}: IconLinkProps) {
  return (
    <Link aria-label={label} className={`text-xl ${className}`} {...props}>
      <FontAwesomeIcon icon={icon} />
    </Link>
  );
}

That one type does three jobs: it borrows everything Link accepts, it removes children because the wrapper renders its own, and it adds icon and label. Borrow, remove, add — that is the whole toolkit.

A default value does not declare a prop

This is the mistake the compiler catches most often. Destructure a prop that the type never mentioned — even with a default — and TypeScript stops you:

type MyLinkProps = ComponentProps<typeof Link>;   // no "icon" in here

const MyLink = ({ icon = faHome, ...props }: MyLinkProps) => (
  //              ^^^^
  // error TS2339: Property 'icon' does not exist on type
  //   'Omit<AnchorHTMLAttributes<HTMLAnchorElement>, keyof LinkProps<any>>
  //    & LinkProps<any> & { children?: ReactNode; } & ...'
  <Link {...props}>
    <FontAwesomeIcon icon={icon} />
  </Link>
);

Writing icon = faHome only says what to use when the prop is missing. It does not add the prop to the type. The fix is the & above.

Common mistakes
  • Retyping props by hand ({ href: string; children: React.ReactNode }). It drifts the moment the inner component changes, and you silently lose every prop you forgot.
  • Forgetting ...props on the element. The types promise onClick works, and it is quietly dropped.
  • Spreading before your own prop: {...props} className="..." overwrites whatever the caller passed. Spread first, or merge the two.
  • Expecting a default value to change the type. It never does. src = "/logo.svg" does not make a required prop optional — that needs Omit. And icon = faHome does not bring a prop into existence — that needs &, and you will see TS2339: Property 'icon' does not exist until you add it.
  • Forgetting to Omit children when your wrapper renders its own. The type still advertises children, so callers pass them and they vanish — JSX children written between your tags always beat a children arriving through a spread.
Next: look at ComponentProps vs ComponentPropsWithoutRef, and at how forwardRef fits in.

03 · 2026-09-21 · React

Components and Props

Concept. A component is a function that returns JSX. Props are its arguments, passed as one object. That is the whole idea — if you can write a function, you can write a component.

// components/Greeting.tsx
export default function Greeting({ name }: { name: string }) {
  return <p>Hello, {name}!</p>;
}

// used as:  <Greeting name="Sam" />

The name must start with a capital

JSX decides what you meant by the first letter. <Greeting /> is your component; <greeting /> is an HTML tag React has never heard of. It fails silently — nothing renders, no error.

children is just another prop

Whatever you put between the tags arrives as children. That is what makes components composable:

// components/Card.tsx
import type { ReactNode } from "react";

export default function Card({
  title,
  children,
}: {
  title: string;
  children: ReactNode;
}) {
  return (
    <article className="rounded border p-4">
      <h3>{title}</h3>
      {children}
    </article>
  );
}

// <Card title="Hello"><p>Any JSX at all.</p></Card>

Let callers extend your styles

A reusable component should accept a className and merge it, so call sites can tweak spacing without forking the component:

export default function Button({
  className = "",
  children,
}: {
  className?: string;
  children: ReactNode;
}) {
  return (
    <button className={`rounded bg-blue-600 px-4 py-2 ${className}`}>
      {children}
    </button>
  );
}
Common mistakes
  • A lowercase component name in JSX. Renders nothing and reports nothing. Always PascalCase.
  • Replacing className instead of merging it. Callers then fight your component with !important.
  • Forgetting children in the props. The content you nested is simply discarded.
  • Mutating a prop. Props are read-only inputs. Derive a new value instead.
Next: learn ComponentProps so you stop hand-writing prop types — see Typing Props.

02 · 2026-09-20 · Rendering

Hydration Errors

Concept. Next.js renders your page to HTML on the server, sends it, then React runs in the browser and builds the same tree again to attach event handlers. That second pass is hydration. If the two versions disagree, you get a hydration error.

The analogy: the server mails a filled-in form, and the browser fills in its own copy to compare. Any difference — one word, one attribute — and React complains, because it can no longer trust the HTML it was given.

Why it happens

  • Values that change between the two runs: Date.now(), Math.random(), new Date().toLocaleString().
  • Browser-only APIs: localStorage, window, matchMedia. They do not exist on the server.
  • Browser extensions. Password managers, translators and grammar checkers inject attributes into <html> and <body> before React looks. The server HTML never had them, so React sees a mismatch — in code that is completely correct.

The extension case: suppress it, on those two tags only

// app/layout.tsx
export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en" suppressHydrationWarning>
      <body suppressHydrationWarning>{children}</body>
    </html>
  );
}

suppressHydrationWarning silences the mismatch for one element, one level deep — its own attributes and text, not its descendants. On <html> and <body> that is exactly the blast radius you want: it covers the attributes extensions add, and nothing of your own.

Your own client-only values: render them after mounting

Here suppressing is the wrong fix — the mismatch is real. Render the server-safe version first, then update:

"use client";

import { useEffect, useState } from "react";

export default function LastSeen() {
  const [time, setTime] = useState<string | null>(null);

  useEffect(() => {
    setTime(new Date().toLocaleTimeString());
  }, []);

  // Server and first client render agree: both render null.
  return <span>{time ?? "--:--:--"}</span>;
}
Common mistakes
  • Sprinkling suppressHydrationWarning around to make warnings go away. It hides real bugs, and the mismatched DOM stays wrong. Use it for attributes you do not control.
  • Expecting it to cover children. It is one level deep only.
  • Chasing a hydration error that only you can reproduce. Retry in a private window with extensions off — that tells you in seconds whether it is your code.
  • Reading localStorage during render. Undefined on the server, a value in the browser: a guaranteed mismatch. Read it in useEffect.
Next: read about Server vs Client Components — knowing which code runs where prevents most of these.

01 · 2026-09-20 · Fonts

next/font

Concept. next/font downloads a font at build time and serves it from your own domain. No request to Google at runtime, no layout shift as the text re-renders, and nothing leaks to a third party.

// app/layout.tsx
import { Geist } from "next/font/google";

const geist = Geist({ subsets: ["latin"] });

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en" className={geist.className}>
      <body>{children}</body>
    </html>
  );
}

You call the font as a function, then apply the className it hands back. Putting it on the root layout applies it to the whole app.

Two or more fonts: use CSS variables

className only lets you apply one font. Ask for a variable instead and you can reference each font wherever you like:

// app/layout.tsx
import { Oswald, Libre_Franklin } from "next/font/google";

const title = Oswald({ subsets: ["latin"], variable: "--font-title" });
const body = Libre_Franklin({ subsets: ["latin"], variable: "--font-body" });

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en" className={`${title.variable} ${body.variable}`}>
      <body>{children}</body>
    </html>
  );
}
/* app/globals.css -- hand the variables to Tailwind as tokens */
@theme inline {
  --font-title: var(--font-title);
  --font-body: var(--font-body);
}

/* now: class="font-title"  and  class="font-body" */

A font name with a space becomes an underscore: Libre Franklin is Libre_Franklin. For a font file of your own, use next/font/local and point it at the file.

Common mistakes
  • Adding a <link> to Google Fonts. That is the old way: an extra round trip, a flash of unstyled text, and the visitor’s IP sent to Google.
  • Calling the font inside the component. It must sit at module scope, as above, or the build fails.
  • Omitting subsets. Required for Google fonts, and it keeps the file small.
  • Declaring a variable and then forgetting to use it. Nothing changes and nothing errors — the variable is defined but no CSS reads it.
