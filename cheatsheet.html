#12 · 2026-09-21 · Pages

Is a subpage like /about just a React component, or does it need special syntax?

Short answer: it’s a plain React component. There is no special syntax inside the file. The “magic” is entirely in where the file lives and what it’s called, plus one rule: the component must be the file’s default export.

The three rules

  • Folder name = URL. app/about/ → /about.
  • File name must be exactly page.tsx (lowercase). That’s what makes the folder a real, visitable URL.
  • export default a component. Next.js looks for the default export and renders it. The function’s name doesn’t matter — Page, AboutPage, anything.

The complete file

// app/about/page.tsx
export default function AboutPage() {
  return (
    <main>
      <h1>About us</h1>
      <p>We are a small team learning Next.js.</p>
    </main>
  );
}

That’s it. No import, no registration, no router config. Save it and visit http://localhost:3000/about. Your app/layout.tsx wraps it automatically, so your header and footer appear around it for free.

Optional extras (not required)

A page can do a few things a normal component can’t, but you only add them when you need them:

// app/about/page.tsx
import type { Metadata } from "next";

// 1. Sets the browser tab title and SEO description for this page.
export const metadata: Metadata = {
  title: "About",
  description: "Who we are",
};

// 2. Pages are Server Components by default, so they may be async
//    and fetch data directly.
export default async function AboutPage() {
  return <h1>About us</h1>;
}
  • Server Component = a component that runs on the server and sends finished HTML. That’s the default for every page. It means no useState or onClick in the page itself — put interactive bits in a separate component marked "use client".
  • params / searchParams props only matter for dynamic routes like [slug] or ?q=. Both are Promises since Next.js 15 — see entry #11.
Common beginner mistakes.
  • Empty page.tsx → error “The default export is not a React Component”. An empty file has no default export.
  • Named export instead of default (export function About()) → same error. It needs the word default.
  • Wrong filename (About.tsx, Page.tsx, index.tsx) → a 404. index.tsx is the old Pages Router habit.
  • Adding <html>/<body> in a page → those belong only in the root layout.
Next step: link to it from your header with <Link href="/about"> from next/link (not a plain <a>) — that’s the linking-and-navigating lesson.

#11 · 2026-09-21 · Routing standards

What are the industry standards for routing in Next.js?

The one-line version: App Router, folders are URLs, a route only exists when you add page.tsx, and everything else is a small set of reserved filenames that each do one job. Master those and you’ve got 90% of it.

1. Rule zero: App Router, not Pages Router

Next.js has two routing systems. app/ is the current one and the only one you should learn. pages/ still works for old projects but gets no new features.

How to spot an outdated tutorial in three seconds. If you see any of these, close the tab: pages/, getServerSideProps, getStaticProps, _app.js, _document.js, next/router (the current one is next/navigation). This is the single biggest source of confusion for people learning Next.js in 2026 — most of the internet still describes the old system.

2. The mental model: two rules

app/blog/authors/page.tsx   →   /blog/authors
    ^^^^ ^^^^^^^ ^^^^^^^^
    |    |       |
    |    |       ’— RULE 2: a folder becomes a real URL only when it
    |    |                  contains page.tsx (or route.ts for an API)
    ’———’————————— RULE 1: folder names are URL segments

Rule 2 is the one that relaxes people: you can put anything you like inside app/ without creating a route. A utils.ts, a component, a test file — none of them are reachable by URL. The docs call this colocation, and it’s safe by design.

3. The reserved filenames

These names are the API. Each does exactly one job, and they must be lowercase exactly as written — Page.tsx is just a normal file.

page.tsx        the actual page. Its presence = this URL exists.
layout.tsx      shared shell, wraps this segment and everything under it.
                Keeps its state across navigations (your header lives here).
loading.tsx     skeleton shown while the page loads. One file = automatic
                Suspense boundary. Cheapest UX win in the framework.
error.tsx       error boundary for this segment. Must be a Client Component.
not-found.tsx   shown by notFound() or an unmatched URL.
route.ts        an API endpoint instead of a page. Can't coexist with page.tsx.
template.tsx    like layout, but remounts on every navigation. Rare.
default.tsx     fallback for parallel routes. Rarer.

They nest in a fixed order, which is worth picturing once:

layout
 └ template
    └ error          (catches everything below it)
       └ loading     (shows while everything below is pending)
          └ not-found
             └ page  (or the next layout down)

So an error.tsx in app/events/ catches failures anywhere under /events while the header and nav stay on screen. That’s the payoff of nested routing: a broken page breaks a panel, not the whole site.

4. Dynamic segments — and the v16 gotcha

app/events/[slug]/page.tsx      →  /events/summer-camp
app/shop/[...slug]/page.tsx     →  /shop/a, /shop/a/b        (catch-all)
app/docs/[[...slug]]/page.tsx   →  /docs, /docs/a, /docs/a/b (optional catch-all)
params is a Promise now. It was a plain object up to Next.js 14. Every older tutorial destructures it directly, and that silently breaks. You must await it. 
// app/events/[slug]/page.tsx  — the v16 way
export default async function Page(props: PageProps<"/events/[slug]">) {
  const { slug } = await props.params;
  return <h1>{slug}</h1>;
}

PageProps is global — no import needed, same as the LayoutProps<"/"> already sitting in your layout.tsx. You give it the route string and it types params for you. searchParams (the ?q=… part) is a Promise too.

5. Two organising tools everyone uses

(group)     round brackets — groups files WITHOUT adding a URL segment
_folder     leading underscore — opts the folder out of routing entirely

Route groups are the real industry pattern, and the reason is layouts. Once your app has a public side and a logged-in side, they need different shells:

app/
  (marketing)/
    layout.tsx        ← public header + footer
    page.tsx          → /
    about/page.tsx    → /about
  (app)/
    layout.tsx        ← sidebar, requires login
    feed/page.tsx     → /feed
    trainees/page.tsx → /trainees

Note the URLs: (marketing) and (app) never appear. They exist purely so two sets of pages can have two different layouts. That’s the thing route groups are for, and you’ll want it the moment trainees log in.

Private folders (_components, _lib) are for colocating a component used by exactly one route. You don’t strictly need them — colocation is already safe — but they signal “implementation detail, not a route” and protect you from clashing with future Next.js filenames.

6. Where components live: the split everyone converges on

used by ONE route          →  app/events/_components/EventCard.tsx
used by MANY routes        →  components/
the app shell              →  components/layout/     ← you already have this
generic primitives         →  components/ui/
non-React helpers          →  lib/  (db.ts, formatDate.ts, auth.ts)

Next.js is officially unopinionated here — the docs say so outright. But that list is what most teams land on, and you’ve already got the important half of it from entry #5.

7. Naming conventions

app/ folders      lowercase-kebab-case    /event-details   not  /eventDetails
reserved files    exact lowercase         page.tsx         not  Page.tsx
components        PascalCase              EventCard.tsx
helpers           camelCase               formatDate.ts

Kebab-case URLs are a web convention older than Next.js: URLs are case-sensitive on Linux servers, and search engines read hyphens as word separators while they read camelCase as one word.

8. Two more current-version facts

  • middleware.ts is now proxy.ts. Renamed in Next.js 16 — same functionality, new name, sits at the project root beside app/. It runs before routes render, so it’s where auth redirects go. Every tutorial you find will say “middleware”. There’s a codemod: npx @next/codemod@canary middleware-to-proxy .
  • typedRoutes: true is stable and is becoming the default expectation on TypeScript projects — it turns a bad href into a build error. See entry #10.

9. What this means for your app

Right now app/ holds exactly one route. Based on your MyAppToDoList.md, here’s the shape to grow into:

app/
  layout.tsx                    ← root shell (you have this)
  page.tsx                      → /
  about/page.tsx                → /about
  contact/page.tsx              → /contact
  feed/
    page.tsx                    → /feed
    loading.tsx                 ← skeleton while posts load
  trainees/
    page.tsx                    → /trainees
    [id]/page.tsx               → /trainees/42
  events/
    page.tsx                    → /events
    [slug]/
      page.tsx                  → /events/summer-camp
      not-found.tsx             ← "no such event"
  api/
    events/route.ts             → /api/events

Don’t build this now. Add app/about/page.tsx, see /about work, and stop. Route groups, parallel routes and intercepting routes (@modal, (.)photo) are real and standard, but they solve problems you don’t have yet. Structure earns its complexity; it never arrives ahead of it.

Next step: create app/about/page.tsx with three lines in it, then add app/about/loading.tsx containing the word “Loading…”. Two files, and you’ve used the two most important conventions in the framework.

#10 · 2026-09-21 · Routing

Can Next.js build my nav automatically from my routes?

Short answer: no, and that’s deliberate. There is no getRoutes() in Next.js — not in v16, not in any version. But there is a feature that checks your hand-written nav against the real routes and fails the build on a typo, which is the genuinely useful half of what you’re asking for.

1. Why there’s no route list to read

Three reasons, and they compound:

  • Your app/ folder doesn’t exist in production. next build compiles your pages into JavaScript bundles and ships those. There is no directory left to scan at runtime.
  • Dynamic routes can’t be counted. app/blog/[slug]/page.tsx is not one route — it’s every blog post that will ever exist. Which of those belongs in a nav bar?
  • The filesystem doesn’t know what you’d want anyway. It can’t tell you the order, the label (is app/ueber-uns/ called “About” or “Über uns”?), or which pages to hide — your privacy policy, a thank-you page, a 404.
Analogy: the floor plan knows every room in the building. It does not know which ones belong on the lobby directory, what to call them, or in what order. That is an editorial decision, and only you can make it.

2. The tempting idea that will cost you an evening

import fs from "node:fs";
const routes = fs.readdirSync("./app");   // <- don't

This works in npm run dev, which is exactly what makes it dangerous. It dies on deploy (no source directory), gives you folder names rather than labels, has no ordering, can’t express [slug], and drags Node-only APIs into your component tree. If you find yourself reaching for fs to solve a routing problem, stop.

3. Level 1 — one array, one place to edit

This is what real Next.js apps do. It is not a workaround; it’s the right answer.

// components/layout/header/navItems.ts
export const navItems = [
  { href: "/", label: "Home" },
  { href: "/about", label: "About" },
  { href: "/services", label: "Services" },
  { href: "/blog", label: "Blog" },
  { href: "/contact", label: "Contact" },
];
// components/layout/header/HeaderMain.tsx
import { navItems } from "./navItems";

<ul className="lg:flex lg:gap-3">
  {navItems.map((item) => (
    <li key={item.href}>
      <LinkTag href={item.href}>{item.label}</LinkTag>
    </li>
  ))}
</ul>

Five hand-written <li>s become one loop. Adding a page is now a one-line edit in one file — and the footer can import the same array, so header and footer can never drift apart. This is also where key from entry #4 finally earns its keep: key={item.href}, because hrefs are unique and stable.

4. Level 2 — let Next.js check the list for you

This is the closest thing to what you asked for. Turn on typed routes:

// next.config.ts
const nextConfig: NextConfig = {
  typedRoutes: true,
};

Next.js scans app/ at build time and generates a type listing every route that exists. Then type your array with it — this example is straight out of the bundled docs:

// components/layout/header/navItems.ts
import type { Route } from "next";

type NavItem<T extends string = string> = {
  href: T;
  label: string;
};

export const navItems: NavItem<Route>[] = [
  { href: "/", label: "Home" },
  { href: "/about", label: "About" },
  { href: "/blog", label: "Blog" },
];

Now href: "/abuot" is a compile error, not a 404 a visitor finds for you. You still write the nav by hand, but the filesystem becomes the referee. Automatic checking instead of automatic generation — and checking is the part that actually prevents bugs.

Careful with the order you do this in. Your app/ folder currently contains exactly one route — app/page.tsx. There is no /about, no /blog. (That’s why all five links in your header point at /.) Switch on typedRoutes today and every one of those hrefs becomes a type error — correctly. Create the pages first, then turn it on.

5. Level 3 — genuinely generated, when pages come from data

There is a case where the nav should build itself: when the pages don’t come from files at all. If your events live in a database, the filesystem has one route — app/events/[slug]/page.tsx — and the data is the source of truth:

// app/events/[slug]/page.tsx
export async function generateStaticParams() {
  const events = await getEvents();
  return events.map((event) => ({ slug: event.slug }));
}

The same query feeds a generated list of event links. For your app that means: Events and the Feed are Level 3 (generated from data), while Home / About / Services / Contact stay Level 1 (a hand-kept array). Almost every real site is this mix, and knowing which half you’re in is the actual skill.

6. What you’ll want next: highlighting the current page

The moment the nav is a loop, you’ll want the active link to look different. That needs the current URL, which means usePathname:

"use client";

import { usePathname } from "next/navigation";
import { navItems } from "./navItems";
import LinkTag from "../shared/LinkTag";

export default function NavList() {
  const pathname = usePathname();

  return (
    <ul className="lg:flex lg:gap-3">
      {navItems.map((item) => (
        <li key={item.href}>
          <LinkTag
            href={item.href}
            className={pathname === item.href ? "bg-foreground/10" : ""}
            aria-current={pathname === item.href ? "page" : undefined}
          >
            {item.label}
          </LinkTag>
        </li>
      ))}
    </ul>
  );
}

Two things the docs are explicit about, and both will bite you otherwise:

  • usePathname is Client-only. Reading the current URL from a Server Component is intentionally unsupported — it’s what lets layouts keep their state across navigations. So this file needs "use client" at the very top.
  • Keep it small. Don’t put "use client" on HeaderMain — split just the list into its own component, as above. The logo and the shell stay server-rendered. The docs are clear that Client Components aren’t a de-optimisation, but there’s still no reason to ship more JavaScript than the interactive bit needs.

aria-current="page" is the free accessibility win: it tells a screen reader which link is the current page, instead of leaving that information in the colour alone.

Next step, in this order: (1) create app/about/page.tsx and app/contact/page.tsx so the routes are real; (2) move the nav into navItems.ts and map over it; (3) then switch on typedRoutes and watch it catch a deliberate typo. Doing it in that order means every step passes instead of fighting you.

#9 · 2026-09-21 · Tailwind v4

Can I write @utility .container with a dot?

No. Drop the dot: @utility container { … }. And this isn’t a style preference — it is hard-failing your site right now.

1. What’s happening on your machine this second

I requested localhost:3000 and got back a 500 error page instead of your site. Tailwind refused to compile the stylesheet:

CssSyntaxError: tailwindcss: app/globals.css:1:1:
  `@utility .container` defines an invalid utility name.
  Utilities should be alphanumeric and start with a lowercase letter.

One bad character in a CSS file took the whole page down — because layout.tsx imports globals.css, and a module that fails to build fails everything that imports it. Good news: the message names the file, the directive and the rule, which is about as helpful as an error gets.

2. Why the dot is wrong: name position vs selector position

Almost everywhere in CSS you write a selector — a pattern that matches elements. .container, #main, a:hover. The dot means “class”. After years of CSS your fingers type it automatically.

But @utility is not a selector position — it is a name position. You aren’t saying “style the elements matching .container”; you are saying “define a utility called container” and letting Tailwind generate the selector for you.

You already know two other name positions, and you’d never put a dot in them either:

@keyframes slide-in { ... }     not  @keyframes .slide-in
@font-face { font-family: Oswald }   you name it, you don't select it
@utility container { ... }      not  @utility .container

.container { ... }              ← THIS one is a selector. Dot required.
Analogy: naming a new tool versus reaching for one on the shelf. @utility container is engraving “container” on the handle. .container { } is walking to the shelf and picking up the one labelled that. You don’t engrave the shelf label onto the handle.

3. The fix

/* app/globals.css */
@utility container {
  margin-inline: auto;
  padding-inline: 1rem;
}

Your @apply mx-auto version works too — @apply is allowed inside @utility — the dot was the only problem. But once you’re writing a utility definition, plain CSS properties are usually clearer: margin-inline: auto says exactly what it does, while @apply mx-auto makes the reader translate a shorthand back into the thing it already was.

4. The naming rules, read off the error message

“Alphanumeric and start with a lowercase letter” rules out more than the dot:

@utility container      OK
@utility content-grid   OK   (hyphens are fine inside the name)
@utility tab-4          OK

@utility .container     no — dot is a selector
@utility Container      no — must start lowercase
@utility 2col           no — must start with a letter

Naming an existing utility — like container — extends it rather than replacing it. That’s the whole point, and it’s the fix for the duplicate-.container race from entry #8: instead of two rules competing in the stylesheet, there is now one utility that Tailwind owns and you added to.

5. How to check it worked

Reload the page — if the 500 is gone, Tailwind compiled. Then look at the generated CSS (DevTools → Sources, or the <link> in view-source) and search for margin-inline. You want to see your declarations merged into the container rule, not sitting in a second competing block.

Habit worth forming: when a page suddenly 500s right after you edited CSS, read the terminal running next dev before touching anything else. CSS build errors show up there in full, while the browser often shows only a generic error page. The answer was sitting in that log the whole time.

6. Also: the hydration fix landed

layout.tsx is now exactly right — cz-shortcut-listen gone, suppressHydrationWarning on both <html> and <body>. One thing I spotted in the dev log worth naming, because you clearly tried it on the way:

Received `true` for a non-boolean attribute `cz-shortcut-listen`.
… and later in the HTML:  suppresshydrationwarning="true"
                            ^^^^^^^^^^^^^^^^^^^^^^^^ all lowercase — React didn't recognise it

That second one is the tell that a prop name was mistyped in casing. React props are camelCase; anything it doesn’t recognise it passes through to the DOM as a literal attribute, lowercased. So suppresshydrationwarning silently became a meaningless HTML attribute instead of the React feature — and then showed up in the mismatch diff as yet another unexpected attribute. If a React prop appears in view-source, it wasn’t a real prop. Real ones are consumed, not printed.

Next step: with container finally owned by one definition, swap the hand-written <div className="container"> in HeaderMain and FooterMain over to your <Container> component. That closes the loop from entry #8 — one component, one utility, one place to change the page width.

#8 · 2026-09-21 · React types

How do I type a plain <div> wrapper like Container?

Short answer: ComponentProps<"div"> — the same helper you used for LinkTag and Logo, but with a string instead of typeof Something. The whole type is one line, and you don’t declare className or children at all.

1. The errors

Container.tsx(2,37): error TS1005: ';' expected.
Container.tsx(3,16): error TS1109: Expression expected.

Both point at the same two lines, and they are parser errors — TypeScript couldn’t even finish reading the file, so it never got as far as checking your logic. That’s why the messages are so unhelpful: the compiler is lost, not disagreeing.

2. Three separate mistakes in two lines

type ContainerProps = HTMLDivElement{
                                    ^ (1) missing &
                      ^^^^^^^^^^^^^^ (2) wrong type entirely
    children: React.nodeElement
              ^^^^^^^^^^^^^^^^^ (3) doesn't exist — it's React.ReactNode
};

(1) Missing &. You can’t write a type and an object type side by side. To combine two types you need the intersection operator: A & { … }. That’s the literal syntax error — but fixing it would not fix the file, because of (2).

3. The one worth really understanding: an element is not its props

HTMLDivElement is the live DOM node — the object the browser creates and hands you from document.querySelector("div"). It has .innerHTML, .scrollTop, .offsetWidth, .click() — a couple of hundred members describing a div that already exists on a page.

A props type is the opposite direction: the list of attributes someone may write in JSX before anything exists.

Analogy: HTMLDivElement is the finished car in the driveway — odometer, current speed, engine temperature. The props type is the order form at the dealership — colour, trim, options. Same car, opposite ends of its life. You handed the customer an engine block and asked them to fill it in.

Where HTMLDivElement is correct — and you will meet it in real code — is as a type argument, answering “what kind of node does this point at?”:

const ref = useRef<HTMLDivElement>(null);              // "this ref will hold a div"
type X = React.HTMLAttributes<HTMLDivElement>;        // "attributes valid on a div"
                              ^^^^^^^^^^^^^^ inside the brackets: fine
type Y = HTMLDivElement;                              // as the props type: never

4. React.nodeElement → React.ReactNode

There is no nodeElement in React. The three names actually worth knowing:

ReactNode        anything React can render:
                 string | number | JSX | array | null | undefined | boolean
                 → this is what children is

ReactElement     specifically a JSX element. Narrower — rejects a plain string.
                 Only use it when you truly need to forbid text.

ComponentProps<T> the props of T, where T is a component OR an HTML tag name.

5. The fixed component

// components/layout/shared/Container.tsx
import type { ComponentProps } from "react";

type ContainerProps = ComponentProps<"div">;

const Container = ({ className = "", children, ...props }: ContainerProps) => {
  return (
    <div className={`container ${className}`} {...props}>
      {children}
    </div>
  );
};

export default Container;

The body you already had was completely right — destructure className with a default, merge it, forward the rest. Only the type line was wrong. Two things to notice:

  • ComponentProps takes either a component or a tag name. ComponentProps<typeof Link> for a component; ComponentProps<"div">, <"button">, <"a"> for plain HTML. Same helper, both worlds — that’s the bit you were missing.
  • You don’t declare className or children. They’re already in there, along with id, onClick, style, every aria-* and every data-*. That’s why the whole thing collapses to one line.

Beginner trap right after this one: once ComponentProps<"div"> compiles, it is tempting to add & { children: React.ReactNode } “to be safe”. Don’t — you’d be narrowing an optional prop into a required one and forcing every caller to pass children.

6. Bonus: your .container CSS is racing Tailwind

Since the component applies container, I pulled the compiled stylesheet off your dev server. There are two .container rules in it:

.container { width: 100%; }                                  ← Tailwind's own utility
@media (min-width: 40rem) { .container { max-width: 40rem } } ← ...and its breakpoints
@media (min-width: 48rem) { .container { max-width: 48rem } }
...
.container { margin-inline: auto; }                          ← YOURS, from globals.css

They happen not to collide — different properties — so it works today. But hand-writing a class that Tailwind also generates is a race you win only by luck: the day you both set the same property, whichever rule is printed last wins. In Tailwind v4 the supported way to extend a built-in utility is @utility:

/* app/globals.css — replaces .container { @apply mx-auto; } */
@utility container {
  margin-inline: auto;
  padding-inline: 1rem;
}

That extends the real utility instead of competing with it. I added padding-inline because you almost certainly want it: Tailwind’s container ships with no horizontal padding and no centering — that surprises everyone coming from Bootstrap — so right now your text touches the screen edge on a phone.

7. It isn’t used yet

Nothing imports Container — HeaderMain and FooterMain still hand-write <div className="container">. Swapping them over is the point of the exercise:

<div className="container lg:flex lg:justify-between lg:items-center lg:gap-4">
<Container className="lg:flex lg:justify-between lg:items-center lg:gap-4">

This is also the honest answer to “does Container earn its keep?” — with two call sites, barely. It pays off the moment you want to change the page width everywhere at once, which is exactly the kind of thing you will want. Fine to keep.

Next step: hover ComponentProps<"div"> in VS Code and press F12 to jump into React’s type definitions. Seeing that these are just ordinary types someone wrote in a .d.ts file — not compiler magic — is the moment TypeScript stops feeling like a wall.

#6 · 2026-09-21 · Typing wrappers

Why does <Logo /> demand a src when the component already has one?

One-sentence answer: your props type says “Logo accepts everything Image accepts” — and src is required on Image, so it’s now required on Logo too, even though Logo ignores it.

1. The exact error

  Property 'src' is missing in type '{ alt: string; loading: "eager"; }'
  but required in type '{ src: string | StaticImport; alt: string; ... }'

Read it as two halves. “in type { alt, loading }” is what you passed at the call site. “required in type { src, alt, ... }” is what Logo asked for. TypeScript is not confused about your Image — it never looked inside Logo at all.

2. The idea worth keeping: a props type is a contract, not a description

type LogoProps = ComponentProps<typeof Image>;   // "callers must pass everything Image needs"

const Logo = ({ alt }: LogoProps) => {           // "...but I only use alt"

Those two lines disagree. The type is a promise to the outside world about what callers must hand you. Destructuring only { alt } does not soften that promise — it just means you quietly bin everything else. TypeScript enforces the promise you wrote, not the one you meant.

Analogy: the props type is the form on the counter. You printed “passport number: required” on it, then decided you’d never read that box. The clerk still refuses the form until it’s filled in. If you don’t need it, take it off the form.

3. Why LinkTag works and Logo doesn’t

Same ComponentProps line, opposite outcome — because the two components have opposite jobs:

                    LinkTag                Logo
who decides href/src?   the CALLER             the COMPONENT
every use differs?      yes (/about, /blog)    no (always the one logo)
so the prop should be   kept, required         removed from the type

LinkTag is a pass-through wrapper — it adds styling and forwards the decision. Logo is a preset wrapper — it has already made the decision. Copying the type from a pass-through into a preset is exactly where this went wrong.

4. The fix: Omit what the component owns

Read Omit<T, "a" | "b"> as “type T, minus these props”:

// components/layout/shared/Logo.tsx
import Image from "next/image";
import type { ComponentProps } from "react";

type LogoProps = Omit<ComponentProps<typeof Image>, "src" | "width" | "height" | "alt"> & {
  alt?: string;
};

const Logo = ({ alt = "ASEK Logo", ...props }: LogoProps) => {
  return (
    <Image
      src="https://asek.academy/wp-content/uploads/2026/09/Main_Logo_Lock.svg"
      width={230}
      height={77}
      alt={alt}
      {...props}
    />
  );
};

export default Logo;

Line by line:

  • "src" | "width" | "height" come off because Logo owns them. Nobody should be able to point your Logo at a different picture, and a caller passing width={50} without a matching height would squash it. Need a smaller logo? className="w-32 h-auto".
  • "alt" comes off and gets added back as optional (alt?: string) with a default. On Image, alt is required — rightly, since nobody can guess what an arbitrary photo shows. But a logo always shows the same thing, so the component can answer for itself. A caller can still override it.
  • Everything else — className, loading, onClick, quality — stays available, correctly typed, for free.

Simpler alternative: a component with a fixed src is barely “an Image” any more. Writing the contract out by hand — type LogoProps = { className?: string; alt?: string }; — is shorter and tells the reader at a glance what Logo can do. Both are correct; Omit teaches you more.

Short answer: the idea is right — wrapping next/link in your own component is a normal, good thing to do. But there are two real errors (TypeScript won’t compile it, and the folder name will break a Linux deploy) and two design choices that will bite you in a week (text instead of children, and a stray key).

0. What you wrote

// Components/Ui/LinkTag.tsx
import Link from "next/link";

// app/page.tsx

First, the good news: this is exactly how a component works. A component is just a function that takes one object of values (props) and returns JSX. You named it with a capital letter (required — lowercase means “plain HTML tag” to React), you exported it, you imported it with the @/ alias, and you forwarded the leftover props with ...props. That last one is a genuinely good instinct.

1. Error one: TypeScript refuses to compile it

Components/Ui/LinkTag.tsx(3,20): error TS7031:

Components/Ui/LinkTag.tsx(3,25): error TS7031:

Why next dev didn’t complain. The dev server strips the types away and runs the JavaScript — it does not stop on type errors. next build does. So “it renders in the browser” is not proof that it compiles. Keep a second terminal on npx tsc --noEmit --watch and you’ll catch these the moment you type them.

You import it as @/Components/Ui/LinkTag. On Windows that works however you capitalise it — Windows treats Components and components as the same folder. Linux does not, and Vercel (and every CI server, and Docker) runs Linux.

Analogy: Windows is a friendly receptionist who finds “mr. smith” when you ask for “Mr. Smith”. Linux is a filing cabinet — wrong case, no such file, build fails. This is the classic “works on my machine” bug, and it only shows up the day you deploy.

The fix is a habit, not a rule: lowercase folder names (components/ui/), PascalCase for component files (LinkTag.tsx). That’s what the Next.js docs and almost every codebase do, so imports stay predictable.

Your version can only ever render a string:

<LinkTag url="/events" text="Events" />                 // fine

<LinkTag url="/events" text={<><Icon /> Events</>} />   // works, but awkward
<LinkTag href="/events"><Icon /> Events</LinkTag>         // what you actually want

React hands every component a free prop called children: whatever sits between the opening and closing tags arrives there automatically. It costs you nothing and it accepts text, an icon, an <Image>, or all three at once.

The same argument applies to url → href. Renaming a prop means everyone reading the code (including you in three weeks) has to learn a private vocabulary. Rule of thumb: when you wrap something, keep that thing’s prop names. Then your component is a drop-in replacement for <Link> and you never have to remember which name goes where.

  • key never reaches your component. React consumes it and strips it out. Inside LinkTag, props.key is undefined — your {...props} spread cannot forward it even if you wanted to.

  <LinkTag key={item.href} href={item.href}>{item.label}</LinkTag>

The trick for typing a wrapper is ComponentProps<typeof Link> — read it as “whatever props Link accepts”. You inherit href, children, className, target, prefetch, replace — all of it, for free, and it stays correct when Next.js updates.

// components/ui/LinkTag.tsx
import Link from "next/link";
import type { ComponentProps } from "react";

type LinkTagProps = ComponentProps<typeof Link>;

export default function LinkTag({ className = "", children, ...props }: LinkTagProps) {
  return (
    <Link
      className={"underline underline-offset-4 hover:no-underline " + className}
      {...props}
    >
      {children}
    </Link>
  );
}

Used like this:

<LinkTag href="https://example.com" target="_blank">Extern</LinkTag>

import Link from "next/link";

#3 · 2026-09-20 · Hydration

Why are suppressHydrationWarning and data-lt-installed important?

One-sentence answer: they are not equally important — suppressHydrationWarning is a legitimate (if optional) fix, and data-lt-installed="true" is a mistake that should be deleted.

The premise is worth correcting first. Neither line is required for the app to work. Both exist to silence a development-only warning caused by a browser extension on your own machine — not by your code.

1. First: what is hydration?

Next.js renders your page to plain HTML on the server and sends that to the browser, so the user sees content immediately. But plain HTML has no behaviour — no click handlers, no state. So React then runs the same components again in the browser, walks over the HTML the server sent, and attaches all the interactivity to it. That second pass is called hydration.

For hydration to work, React needs the HTML in the page to match what it is about to render. If they differ, React does not know which one is correct, so it warns — a hydration mismatch.

Analogy: the server mails you a printed, filled-in form. React arrives later with its own copy and checks them line by line before it wires up the buttons. If a single line differs, React stops and says “someone changed this form”.

2. Where data-lt-installed actually comes from

You did not write it — and neither did Next.js. lt stands for LanguageTool, the grammar-checker browser extension. When you have it installed, it stamps data-lt-installed="true" onto the <html> tag of every page you visit.

The timing is what causes the trouble:

1. Server sends:      <html lang="en" class="...">
2. Extension edits:   <html lang="en" class="..." data-lt-installed="true">
3. React hydrates:    expects step 1, finds step 2  ->  MISMATCH

The extension slips in during the gap between the HTML arriving and React hydrating. React then reports an extra attribute it never rendered.

3. Why hardcoding it is the wrong fix

Adding data-lt-installed="true" to your JSX does make the warning go away — by making the server output match what the extension produces. It is a clever guess, but it backfires four ways:

  • It ships a lie to every visitor. Everyone now receives HTML claiming LanguageTool is installed, including people who have never heard of it.
  • It fixes exactly one extension. Grammarly injects data-gr-ext-installed and data-new-gr-c-s-check-loaded. Dark Reader, password managers and ad blockers each add their own. You would be playing whack-a-mole forever.
  • It breaks in the other direction. Uninstall LanguageTool and now your HTML has an attribute the browser does not — a brand-new mismatch.
  • It solves a problem your users mostly do not have. This warning appears in your dev console because of your browser. Open the site in incognito and it vanishes.

Quick check: open the page in an incognito window (extensions off). If the warning disappears, an extension caused it — not your code.

4. Why suppressHydrationWarning is the right fix here

It tells React, for one element only: “do not compare this one — keep whatever is already in the DOM.” From the Next.js guide:

With suppressHydrationWarning: React keeps whatever is in the DOM and discards the client’s output for that element. The DOM wins.

The property that makes it safe rather than reckless is this: it only works one level deep. Putting it on <html> covers the <html> tag’s own attributes — which is precisely the extension’s blast radius — and does not silence mismatches inside your actual components. Real bugs still get reported.

That is the whole reason this pattern is so common on the root layout, and why libraries like next-themes tell you to add it there.

5. But the syntax is wrong

suppressHydrationWarning="true"   // string "true"  -> TYPE ERROR
suppressHydrationWarning={true}   // boolean true    -> works, but verbose
suppressHydrationWarning          // boolean true    -> correct

In JSX, a bare prop name already means true. Quotes make it a string, and this prop wants a boolean. TypeScript flags it:

app/layout.tsx(25,7): error TS2322: Type 'string' is not assignable
to type 'boolean | undefined'.

This catches people out because in plain HTML disabled="true" works fine. JSX is JavaScript, not HTML — quotes there really do mean a string.

6. What to write instead

<html
  lang="en"
  className={`${oswald.variable} ${libreFranklin.variable} h-full antialiased`}
  suppressHydrationWarning
>
  <body className="min-h-full flex flex-col font-body">{children}</body>
</html>

One bare prop. data-lt-installed is gone.

7. When suppressHydrationWarning is not okay

This is the part that matters long-term. It is an escape hatch, not a fix. Reaching for it whenever a hydration warning appears hides real bugs.

Legitimate Hiding a bug
Browser extensions editing <html> or <body> new Date() or toLocaleDateString() rendered directly
A value you deliberately corrected with an inline script before first paint Math.random() in render
Theme class read from localStorage by a pre-hydration script Reading localStorage or window during render
— Invalid HTML nesting, e.g. a <div> inside a <p>

The pattern: if something outside React legitimately changed the DOM before hydration, suppressing is correct. If your own component renders differently on server and client, suppressing just papers over it — the user still sees the wrong value, now silently.

8. Rule of thumb

Put suppressHydrationWarning on <html> once and never think about it again. Anywhere else, treat each use as something you have to justify out loud.
Next step: read node_modules/next/dist/docs/01-app/02-guides/preventing-flash-before-hydration.md. It works through the honest fix for a real mismatch (dates and dark mode) using an inline script that runs before the first paint — the technique you reach for when suppressing would be cheating.

#2 · 2026-09-20 · Fonts

How do I add a font to layout.tsx?

One-sentence answer: import the font from next/font/google, call it as a function at the top level of the file, then put the object it returns onto an element — either font.className (applies it) or font.variable (declares a CSS variable you use later).

Heads up — your file already has three problems. The imports are there, but nothing actually renders in those fonts yet, and it will not compile. Details in section 3.

1. Why next/font exists at all

The old way to use a Google Font was a <link> tag pointing at fonts.googleapis.com. Two things go wrong with that: the browser has to make a round trip to Google before it knows what the text looks like, so text visibly jumps when the font lands (“layout shift”), and every visitor’s IP address gets sent to Google.

next/font downloads the font file at build time and serves it from your own domain. No request to Google ever leaves the browser. It also measures the font and generates a matched fallback, so the jump is gone.

Analogy: instead of ordering a book from a warehouse every time someone walks in, you keep a copy on your own shelf.

2. The two ways to apply a font

The function returns an object. You use one of two properties on it:

Property What it does Use when
.className A ready-made CSS class that sets font-family right now. Put it on an element and that element uses the font. You have one font for the whole site.
.variable A class that only declares a CSS variable (e.g. --font-body). By itself it changes nothing visually — you still have to consume the variable in CSS. You have two or more fonts and want to switch between them (headings vs body).

You picked .variable, which is the right call for two fonts — but it is the half that needs a second step, and that step is missing.

3. The three problems in your current file

(a) libre_franklin should be Libre_Franklin.

The rule for Google font names: keep the capitals exactly as Google writes them, and replace each space with an underscore. “Libre Franklin” → Libre_Franklin. “Roboto Mono” → Roboto_Mono. TypeScript catches this one for you:

app/layout.tsx(2,18): error TS2724: '"next/font/google"' has no exported
member named 'libre_franklin'. Did you mean 'Libre_Franklin'?

(b) suppressHydrationWarning="true" should be plain suppressHydrationWarning.

It is a boolean prop. In JSX, writing a bare prop name means true. Writing ="true" passes the string "true", which is a type error. (If you needed a real boolean expression you would write {true} with braces.)

(c) globals.css still points at the fonts that used to be there.

This is the big one, and it is why nothing looks different. Your CSS says:

--font-sans: var(--font-geist-sans);   /* nothing declares this any more */
--font-mono: var(--font-geist-mono);   /* nor this */

Those were from the starter template’s Geist fonts. You swapped the fonts in layout.tsx but the CSS is still asking for the old variable names, so it resolves to nothing. And on top of that:

body {
  font-family: Arial, Helvetica, sans-serif;   /* <- hard-coded, wins anyway */
}

So even if the variable name were correct, this line would override it on <body>. This exact combination — a stale variable name plus a leftover hard-coded font-family — is the single most common reason a beginner’s font “does not work” with no error message anywhere.

4. The corrected app/layout.tsx

import type { Metadata } from "next";
import { Oswald, Libre_Franklin } from "next/font/google";
import "./globals.css";

const oswald = Oswald({
  subsets: ["latin"],
  display: "swap",
  variable: "--font-heading",
});

const libreFranklin = Libre_Franklin({
  subsets: ["latin"],
  display: "swap",
  variable: "--font-body",
});

export const metadata: Metadata = {
  title: "Create Next App",
  description: "Generated by create next app",
};

export default function RootLayout({ children }: LayoutProps<"/">) {
  return (
    <html
      lang="en"
      className={`${oswald.variable} ${libreFranklin.variable} h-full antialiased`}
      suppressHydrationWarning
    >
      <body className="min-h-full flex flex-col font-body">{children}</body>
    </html>
  );
}

Line by line, the things worth knowing:

  • The call must be at the top level of the module — not inside the component function. Next.js reads it at build time to download the font; it cannot do that if the call only happens at render.
  • subsets: ["latin"] — which alphabets to ship. Latin only keeps the file small. Add "latin-ext" if you need accented characters beyond basic French/German.
  • display: "swap" — show fallback text immediately, swap in the real font when ready. The docs recommend it; without it the text can be invisible for a moment.
  • No weight needed. Both Oswald and Libre Franklin are variable fonts — one file contains every weight from thin to bold. For a non-variable font TypeScript will force you to pass weight, so you will find out.
  • I renamed the CSS variables by role (--font-heading, --font-body) rather than by family. Your old name --font-oswald-sans was slightly misleading — Oswald is a condensed display face for headings, not a body sans. Naming by role means swapping the family later touches one line.
  • The variable classes go on <html> so the variables exist everywhere. <body> works too — the docs say either is fine.

5. The missing half: wire it up in app/globals.css

You are on Tailwind v4, where there is no tailwind.config.js any more — theme values are declared in CSS inside an @theme block. Naming a font there creates a matching utility class: --font-body gives you font-body.

@theme inline {
  --color-background: var(--background);
  --color-foreground: var(--foreground);

  --font-body: var(--font-body);         /* -> font-body    (Libre Franklin) */
  --font-heading: var(--font-heading);   /* -> font-heading (Oswald)         */
}

body {
  background: var(--background);
  color: var(--foreground);
  /* delete the hard-coded font-family: Arial line that was here */
}

The inline keyword tells Tailwind to paste the variable reference straight through rather than resolving it once at build time — which is what you want here, because the value is supplied at runtime by the class sitting on <html>.

6. Using them

// app/page.tsx
export default function Home() {
  return (
    <main className="p-8">
      <h1 className="font-heading text-5xl uppercase tracking-wide">
        Oswald headline
      </h1>
      <p className="mt-4 text-lg">
        Body text, inherited from the body tag.
      </p>
    </main>
  );
}

font-body sits on <body> and every child inherits it. Headings opt out with font-heading.

7. The single-font shortcut

If you only ever want one font, skip variables and CSS entirely:

import { Libre_Franklin } from "next/font/google";

const libreFranklin = Libre_Franklin({ subsets: ["latin"] });

export default function RootLayout({ children }: LayoutProps<"/">) {
  return (
    <html lang="en" className={libreFranklin.className}>
      <body>{children}</body>
    </html>
  );
}

Note .className, not .variable. Two lines, done. You would still want to delete the font-family: Arial rule.

8. Beginner mistakes, and how to spot each one

Mistake Symptom
Used .variable but never consumed the variable No error at all, font just never appears. Your case.
Left a hard-coded font-family on body Variable is correct, text still wrong. DevTools shows your font crossed out.
Called the font inside the component Build error: font loaders must be called at module scope.
Wrong capitalisation, or a space instead of _ TypeScript error, usually with a “Did you mean…?” hint.
Non-variable font without weight TypeScript says the weight property is missing.
Also kept a <link> to Google Fonts in <head> Works, but downloads the font twice and leaks visitor IPs — the exact thing next/font prevents.

9. How to check it actually worked

Run npx tsc --noEmit for the name and type errors, then open the page, right-click some text → Inspect → Computed tab → look at font-family. It should read something like __Libre_Franklin_abc123. If it still says Arial, the CSS wiring is still wrong.

Next step: add a local font file with next/font/local — same .className / .variable idea, but you point src at a .woff2 inside your project. That is how you would ship a paid or custom typeface.

#1 · 2026-09-20 · Project structure

How do I organise the folder structure and assets in Next.js?

One-sentence answer: app/ is your URL map, public/ is your static files — and everything else is your own choice, because Next.js is deliberately unopinionated about it.

1. The mental model (learn these two rules)

  • A folder inside app/ = a piece of the URL. So app/blog/authors/ becomes /blog/authors.
  • But a folder is not a real page until it contains page.tsx (or route.ts for an API).

That second rule is the one beginners miss, and it's liberating: any other file you drop into a route folder is invisible to the router. This is called colocation — it's why you can park a component right next to the page that uses it without accidentally creating a URL.

2. A good starting structure

leannextjs/
|- app/                      <- ROUTES ONLY
|  |- layout.tsx             root layout (html, body, fonts)
|  |- page.tsx               -> /
|  |- globals.css            global styles, imported by layout
|  |- favicon.ico            special file: becomes the tab icon
|  |- blog/
|     |- page.tsx            -> /blog
|     |- loading.tsx         spinner while /blog loads
|     |- error.tsx           error screen for /blog
|     |- [slug]/page.tsx     -> /blog/anything
|
|- components/               <- reusable UI (Button, Card, Navbar)
|- lib/                      <- helpers, data fetching, utils
|- public/                   <- static files served at /
|  |- logo.svg               -> http://localhost:3000/logo.svg
|  |- images/hero.jpg        -> /images/hero.jpg
|
|- next.config.ts
|- tsconfig.json
|- package.json

The names components/ and lib/ mean nothing to Next.js — they are pure convention. Call them ui/ and utils/ if you like. Just be consistent.

3. Three special folder names

Pattern What it does
(marketing) Route group. Groups routes without appearing in the URL. app/(marketing)/pricing/page.tsx is served at /pricing, not /marketing/pricing. Bonus: each group can have its own layout.tsx.
_components Private folder. A leading underscore means "router, ignore me and everything inside me". Not strictly needed (colocation already works), but it makes intent obvious and avoids clashing with future Next.js file names.
[slug] Dynamic segment. Matches any value and hands it to your page via the params prop.

4. Where each kind of asset goes

Asset Put it here
Photos, logos, SVGs, PDFspublic/ — reference it as /logo.svg
Global CSSapp/globals.css, imported once in app/layout.tsx
FontsNo files at all — use next/font/google in the layout
favicon, robots, sitemap, social preview imageInside app/ as favicon.ico, robots.txt, sitemap.ts, opengraph-image.png. Next.js wires them into the HTML for you.
An image used by exactly one pageRight next to that page and imported directly — colocation allows it

5. Using an image — the two ways

import Image from 'next/image'

// A) from public/ - path starts at "/", YOU supply the size
<Image src="/images/hero.jpg" alt="Hero" width={800} height={400} />

// B) static import - Next reads the real size for you
import hero from './hero.jpg'
<Image src={hero} alt="Hero" placeholder="blur" />

Prefer B when you can: the correct width/height come for free and you get a blur-up placeholder. Either way, <Image> auto-converts to WebP, lazy-loads, and serves a device-appropriate size — things a plain <img> will never do.

Why width and height are mandatory: the browser reserves the space before the image arrives, so your page doesn't jump around while loading. That jump has a name — layout shift — and Google measures it.

6. Fonts, the Next.js way

// app/layout.tsx
import { Geist } from 'next/font/google'

const geist = Geist({ subsets: ['latin'] })

export default function RootLayout({ children }) {
  return (
    <html lang="en" className={geist.className}>
      <body>{children}</body>
    </html>
  )
}

Next downloads the font at build time and self-hosts it. No request to Google at runtime → faster, more private, no font-swap flicker. Never hand-write a Google Fonts <link> tag.

7. Beginner traps

  • Putting favicon.ico in public/. In the App Router it belongs in app/.
  • Writing src="./public/logo.svg". The word public is never part of the URL — it's just /logo.svg.
  • Fearing that app/components/ becomes a route. It can't. No page.tsx, no route.
  • Copy-pasting tutorials that use pages/, getServerSideProps or _app.js. That's the old Pages Router. You're on the App Router.
  • Building a deep features/... hierarchy on day one. Start flat; split a folder only once it genuinely annoys you.

8. What about src/?

Optional. Moving app/, components/ and lib/ into a src/ folder keeps the root tidy on bigger projects. public/, next.config.ts, tsconfig.json and .env files always stay at the root. This project doesn't use src/ — for learning, that's one less layer to think about.

9. Free bonus: the @/ shortcut

Your tsconfig.json already maps @/* to the project root, so you never need ../../../:

import Button from '@/components/Button'     // clean, survives a move
import Button from '../../components/Button' // fragile
Next step: create app/about/page.tsx and visit /about. Then add components/Navbar.tsx and render it from app/layout.tsx. Those two moves let you feel both rules at once.
